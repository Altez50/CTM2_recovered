# Сценарный контур торгового учета

Каталог: `runner/trade_harness/scenarios/catalog.json`.
Читаемый каталог всех шагов и ожидаемых чисел: [TRADE_ACCOUNTING_SCENARIOS.md](TRADE_ACCOUNTING_SCENARIOS.md).
Общая фикстура: `runner/trade_harness/scenarios/fixture.json`.
Авторский источник: `runner/trade_harness/build_catalog.py`.

Созданы 150 сценариев в 22 разделах. Они охватывают НСИ, закупки, продажи,
заказы и резервы, склад, возвраты, оплаты, банк и кассу, цены и скидки,
себестоимость, НДС и валюты, розницу, комиссию и ответственное хранение,
межфирменные операции, сборку, планирование, отчеты, жизненный цикл,
обмен, CRM, доставку и маркетплейсы. Служебные подсистемы платформы, обновление
конфигурации, зарплатный и бухгалтерский учет вне торгового контура сюда не входят.

**Это библиотека бизнес-сценариев, а не утверждение о полной реализации УТ11.**
Она не является исчерпывающим тестом всех вариантов 274 документов, всех
функциональных опций и отраслевых интеграций УТ. Для каждой включенной операции
зафиксирован проверяемый профиль: например, FIFO отдельно от средней,
последовательные скидки отдельно от максимальной. Числовые ожидания написаны
независимо от приложения, но пока не подтверждены исполнением этих цепочек в 1С.

## Статусы и правила полноты

- `passed`: конкретный сценарий действительно исполнился и прошел assertions.
- `failed` / `error`: неверный результат или техническая ошибка.
- `blocked`: отсутствует сценарный адаптер. Возможное наличие похожего API не
  дает права считать сценарий реализованным. У некоторых сценариев отсутствует
  именно функциональность, у других еще требуется адаптер и проверка.
- `not_run`: адаптер есть, но сценарий не запускался в этой команде.

В отчете статусы CTM и УТ раздельны. Поле `reference_scenarios_passed` остается
`false`: полного адаптера исполнения этих сценариев в 1С еще нет.
Ранее настроенная живая сверка восьми проведенных документов проверяет только
проекцию начисления задолженности и не заменяет исполнение нового каталога.

32 сценария имеют API-адаптер CTM, остальные 118 явно заблокированы.
Для исполняемых случаев создается новая БД на каждый сценарий через существующие
pytest fixtures. Справочники, документы и платежи создаются через API;
учетные регистры не заполняются тестом напрямую. Проверяются точные остатки,
стоимость, три аналитики долга, оплаты, ОСВ и число движений там, где это
предусмотрено контрактом. Деньги сравниваются через Decimal.

Фикстура использует две организации A/B, два контрагента X/Y, четыре договора,
три склада и один товар. В каждом сценарии собственное пустое учетное состояние.
Пара `debts[договор] = [кредиторская, дебиторская]`; пара
`stock[склад] = [количество, стоимость без НДС]`.

Наличие всех обязательных ID и разделов проверяется по авторскому источнику.
Удаление сценария из JSON, дублирование ID, неизвестный адаптер, отсутствие
ожиданий или необоснованная отметка об исполнении в 1С приводят к ошибке
валидации. Сам по себе успешный `validate` не означает прохождение сценариев.

## Команды

Ниже `python` — интерпретатор с `current/api/requirements-dev.txt`.
В текущем окружении можно заменить его на
`& 'F:\2026f\ctm3\.python\python.exe'`.

Проверить контракты и их ссылки на XML-метаданные:

```powershell
python runner/trade_harness/suite.py validate --metadata 'F:\cf2files\UT_11_5_20_80'
```

Выполнить весь каталог, включая проверку отсутствующей реализации:

```powershell
python runner/trade_harness/suite.py run
```

Сейчас эта команда должна завершаться кодом 1: отсутствие 118 адаптеров не
замаскировано пропусками или фиктивными успешными тестами.

Выполнить реализованную часть для текущей разработки:

```powershell
python runner/trade_harness/suite.py run --implemented-only
```

Код 0 в этом режиме относится только к исполняемой части. В JSON по-прежнему
видны все заблокированные сценарии и `full_scope_passed: false`.
Поле `selected_scope_passed` относится к текущему фильтру сценариев;
`full_scope_passed` может стать true только для всего каталога.

Выбрать раздел, профиль или конкретные ID:

```powershell
python runner/trade_harness/suite.py run --area payments --implemented-only
python runner/trade_harness/suite.py coverage --profile extended
python runner/trade_harness/suite.py run --ids SAL-001,PAY-002
```

Отчет по умолчанию: `data/trade-harness/suite-report.json`. Для запусков тестов
рядом сохраняются JUnit XML и pytest log. Путь можно изменить через `--report`.
Параллельные прогоны должны использовать разные пути отчетов.

Проверить наличие объектов и число проведенных документов в UTrecover:

```powershell
.\runner\trade_harness\run.ps1 -AuditReference
```

Аудит только читает базу; отчет `data/trade-harness/reference-audit.json` явно
указывает `scenario_execution: not_run`. Отсутствие проведенных документов
для какого-либо вида означает отсутствие образцов, а не отсутствие метаданных
или автоматическое прохождение сценария.

Весь backend-suite автоматически включает 32 исполняемых случая.
`verify.py` дополнительно проверяет структуру полного каталога перед тестами.
Для требования полной функциональной готовности используйте `suite.py run`.

## Расширение

1. Изменить определения в `build_catalog.py`, а не только сгенерированный JSON.
2. Пересобрать JSON и читаемый каталог:
   `python runner/trade_harness/build_catalog.py`.
3. Реализовать действие в API-исполнителе и точные наблюдения либо отдельный
   адаптер. Текущий исполнитель допускает только явно реализованные операции.
4. Снять блокировку лишь после реального запуска; описанный сценарий не является
   достаточным основанием для статуса `passed`.
5. Для УТ добавить отдельный адаптер, запускающий цепочку в тестовой копии базы,
   и сохранить результаты/настройки эталона. `UTrecover` пока используется
   только для чтения: создание и проведение всего каталога в ней не производится.

Розничные фискальные операции, маркировка, ЭДО, ЕГАИС, банки и маркетплейсы
заданы с эмуляторами транспорта. Каталог не отправляет реальные чеки,
платежи или документы во внешние системы.
