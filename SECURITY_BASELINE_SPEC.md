# CTM — базовая спецификация безопасности и эксплуатации

Версия: 0.1
Создано: 2026-09-02
Статус реализации: gap; обязательный baseline до новых массовых импортов.
Владелец: требуется назначить.
Связанный аудит: `SPEC_REVIEW.md`.

## 1. Область

Требования распространяются на API, web-клиент, синхронизацию, runner/deploy
скрипты, SQLite/PostgreSQL, импорт/экспорт и production-конфигурацию.

## 2. Секреты и конфигурация

1. Пароли, приватные ключи, JWT/sync tokens и production connection strings не
   хранятся в Git и не имеют рабочих fallback-значений в коде.
2. Все уже попавшие в историю секреты считаются скомпрометированными и ротируются;
   одного удаления из текущей версии недостаточно.
3. Production-режим завершается с ошибкой до старта, если JWT secret, sync token,
   CORS allowlist или обязательные DB credentials отсутствуют/равны dev-default.
4. Demo seed users разрешены только при явном `ALLOW_SEED_DATA=true`; production
   default — `false`. Первый администратор создаётся отдельной bootstrap-командой
   с одноразовым секретом.
5. Секреты не выводятся в логи, UI, exception text или health endpoints.

## 3. Аутентификация, сессии и синхронизация

1. Хранятся только современные password hashes; legacy plaintext сравнение имеет
   ограниченную миграцию и удаляется после неё.
2. Logout/revocation, inactivity timeout и expiration проверяются API-тестами.
3. Sync endpoints всегда fail-closed вне локального dev-режима. Сравнение token
   выполняется constant-time; неуспешные попытки журналируются без значения token.
4. Для публичного контура обязательны TLS и доверенная проверка сертификата.

## 4. Авторизация

1. В репозитории хранится единая RBAC-матрица: entity/action × admin/manager/
   foreman. Backend является источником решения; скрытие кнопки в UI не является
   защитой.
2. Матрица включает create/read/update/delete/restore/copy/import/export/post/
   unpost/calculate/distribute/sync/engineering.
3. Изменение проведённого/распределённого/закрытого документа запрещено через все
   пути, включая import, bulk operation и sync, кроме явно специфицированной
   административной процедуры.
4. Каждый отрицательный сценарий роли имеет автоматический тест с ожидаемым 401
   или 403.

## 5. Импорт, экспорт и инженерные инструменты

1. Импорт выполняет validate/preview до изменений, затем атомарный apply. Ошибка
   любой строки не оставляет частично заменённую табличную часть, если режим
   частичного применения явно не выбран и не отражён в отчёте.
2. Ограничиваются размер файла, число строк, время разбора и распакованный размер
   XLSX/ZIP. Имена/формулы из файла не исполняются.
3. CSV/XLSX/HTML exports экранируют значения и предотвращают formula injection.
4. Инженерная консоль только admin/read-only; фактическое число строк всегда
   `<= MAX_ROWS`, включая пользовательский `LIMIT`; timeout и whitelist нельзя
   обойти CTE, comment, quoted identifier или несколькими statements.

## 6. Аудит и наблюдаемость

1. Каждая операция записи фиксирует actor id/username, action, entity/id, время,
   outcome и безопасный diff/summary. Ошибка записи аудита наблюдаема; политика
   fail-open/fail-closed задаётся явно для класса операции.
2. Логи имеют correlation id, не содержат секреты/полные импортируемые данные и
   имеют документированную retention policy.
3. Health/readiness различают живой процесс, готовность БД, версию сборки и версию
   схемы без раскрытия конфигурационных секретов.

## 7. Поставка, backup и восстановление

1. Перед миграцией создаётся проверяемый backup; restore регулярно тестируется.
2. Для production заданы RPO/RTO, владелец инцидента и rollback релиза/схемы.
3. CI запускает secret scan, dependency scan, backend tests, frontend type/build,
   Playwright smoke и migration/dialect checks.

## 8. Критерии приёмки

1. Secret scan не находит рабочих credentials; ранее опубликованные credentials
   ротированы и отмечены в закрытом incident record.
2. Production не стартует с dev JWT secret, пустым sync token или demo seed.
3. Полная RBAC-матрица проверена API-тестами, включая import/restore/engineering.
4. Импорт проведённого документа возвращает 409/400 и не меняет строки.
5. Авария на середине apply не оставляет частичных изменений.
6. Запрос инженерной консоли с `LIMIT > MAX_ROWS` возвращает не более `MAX_ROWS`.
7. Экспорт значений, начинающихся с `=`, `+`, `-`, `@`, безопасен для spreadsheet;
   HTML special characters не ломают файл.
8. Backup тестовой БД восстановлен автоматически, контрольные суммы/счётчики
   ключевых таблиц совпадают.
