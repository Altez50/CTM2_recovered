## Полученное поведение

Существующий API поддерживает аванс нового пространства приобретений без
дополнительного документа зачета. Платеж 400 создает один факт оплаты,
приобретение 1000 без НДС — один факт начисления. В разрезе организации,
контрагента, договора и объекта общий регистр показывает остаток аванса 0
и долг 600. Дополнительных денежных или складских движений зачета не создается.

| Момент | Аванс | Долг |
|---|---:|---:|
| Платеж 400 до приобретения | 400 | 0 |
| После приобретения 1000 | 0 | 600 |

В прямой схеме приобретение также создает склад 10 / стоимость 1000.
В ордерной схеме физический ордер не погашает аванс и не создает долг;
финансовое приобретение выполняет зачет без второго складского прихода.
Оба порядка оформления проверены. Для услуги возникает расход 1000 и долг 600,
склад не изменяется.

Платежи 0,01 / 400 / 1000 / 1400 проверяют частичный зачет, точное закрытие
и остаток переплаты. Платеж после приобретения уменьшает долг; будущая дата
платежа не меняет отчет на дату до оплаты. Чужая организация, контрагент,
договор или объект сохраняют отдельные долг и аванс.

Повторное проведение платежа или приобретения отклоняется. Отмена оплаты
возвращает долг 1000; повтор восстанавливает 600. Для отмены приобретения
существующая защита требует сначала отменить проведенные оплаты договора.
После отмены обоих документов можно заново провести аванс и приобретение;
результат снова 0 / 600. Это общий зачет внутри аналитического разреза,
без индивидуального распределения аванса между счетами.

## Изменения и API

Производственные сервисы, модели, API и формы менять не потребовалось:
их поведение доказано исполнением. Используются:

- `POST /api/payments/transactions` с `allow_advance=true`, договором и контрагентом;
- проведение/отмена `/api/payments/transactions/{id}/{post|unpost}`;
- приобретение `/api/purchases/acquisitions` на основании согласованного заказа;
- проведение/отмена `/api/purchases/acquisitions/{id}/{post|unpost}`;
- `GET /api/settlements/balance`, включая запрос на конкретную дату.

В существующей форме платежа уже есть «Разрешить аванс по договору».
Сервер требует договор для аванса, проверяет контрагента и права организации;
без разрешения аванса платеж до начисления отклоняется.

Добавлены 33 проверки в `current/api/tests/test_purchase_advances.py`,
реальный API-адаптер PUR-010 и его включение в сценарный набор. Метаданные
исполнения изменены только у PUR-010. Все 150 исходных бизнес-контрактов,
предусловия, действия и числовые ожидания сохранены.

Три fault-проверки внедряют ошибку после фактических записей проведения/
отмены платежа и проведения приобретения. Заголовки, регистры и аудит
откатываются вместе; повтор проходит. Проверены viewer/manager/admin и
ограничения организаций. Существующие блокировки договора используются обоими
видами документов; новых правил блокировок или заявлений о PostgreSQL нет.
