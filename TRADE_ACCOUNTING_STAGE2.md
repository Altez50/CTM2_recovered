# Торговый учет: второй этап, RET-001–RET-005

Изменения от 13.10.2026 подготовлены в рабочем дереве для ревью. Развертывание
и изменения рабочих баз не выполнялись. Предшествующие изменения сохранены.

## Поведение

Добавлены возврат клиента и возврат поставщику, связанные с конкретным
проведенным исходным документом и его строками. Аналитика организации,
контрагента, договора, склада, объекта и сметы наследуется сервером.
Переданные несовпадающие аналитики отклоняются. Договор и принадлежность
склада повторно проверяются при проведении.

Возврат клиента приходует товар по сохраненной исходной себестоимости
продажи, а не по текущей средней цене. Возврат поставщику списывает
себестоимость исходного поступления. Стоимость, количество и аналитики
проверяются по складскому движению основания. Возврат сторнирует начисление
в исходном направлении взаиморасчетов на сумму с НДС; выручка и себестоимость
частичного возврата RET-001 проверяются отдельно: 300 и 200 соответственно.

Лимит применяется к каждой строке основания с учетом всех проведенных
возвратов. Черновики не занимают лимит. При проведении лимит проверяется
заново под блокировкой основания. Проверены два конкурентных возврата:
успешно проводится только один, если их сумма превышает исходное количество.
Суммы и НДС распределяются с округлением до копейки по накопленному количеству,
чтобы дробные возвраты полностью сторнировали исходную сумму.

Списание поставщику и отмена прихода от клиента проверяют количество и
стоимость склада на дату операции и на последующие даты движения. Операции
выполняются транзакционно; искусственная ошибка после записи склада не
оставляет частичных движений. Отмена основания блокируется при проведенных
возвратах, удаление основания — при любых неудаленных возвратах.

Возврат денег — отдельный документ на основании возврата товара. Клиенту
деньги выдаются, от поставщика поступают. В денежном регистре записывается
положительный факт соответствующего направления, во взаиморасчетах —
отрицательная оплата исходного направления. Проверяются сумма возврата
товаров, уже проведенные возвраты денег и доступная сумма в той же аналитике
на дату платежа. В модели первого этапа эта сумма отражается как аванс
покупателя/поставщику. Направления, договоры и объекты не смешиваются.

Проведенные документы нельзя редактировать, удалять или проводить повторно.
После отмены повторное проведение создает ровно один набор движений.
Проведенный возврат денег блокирует отмену возврата товара. Сохранение
доступно администратору и менеджеру, проведение/отмена — администратору.

## API и формы

| API | Назначение |
|---|---|
| `GET/POST /api/goods/returns` | Список с пагинацией и создание возврата |
| `GET/PUT/DELETE /api/goods/returns/{id}` | Чтение, изменение черновика, удаление |
| `POST /api/goods/returns/{id}/post`, `/unpost` | Проведение и отмена |
| `GET /api/goods/returns/{id}/movements` | Склад и взаиморасчеты |
| `GET /api/goods/return-sources/{kind}/{id}` | Основание и оставшееся количество; `exclude_id` исключает текущий возврат |
| `POST /api/goods/return-refunds` | Создание документа возврата денег |
| `GET/PUT/DELETE /api/goods/return-refunds/{id}` | Чтение, изменение черновика, удаление |
| `POST /api/goods/return-refunds/{id}/post`, `/unpost` | Проведение и отмена возврата денег |
| `GET /api/goods/return-refunds/{id}/movements` | Денежные движения и взаиморасчеты |

Создание возврата:

```json
{
  "kind": "customer",
  "source_id": 123,
  "date": "2026-10-13",
  "lines": [{"source_line_id": 456, "quantity": 1}]
}
```

Для поставщика `kind` равен `supplier`, `source_id` указывает поступление.
Количество и идентификатор строки обязательны; цены, НДС и себестоимость
пользователь не задает. Возврат денег принимает `return_id`, `date`, `amount`.

В интерфейсе `/ctm/goods/returns` доступны список и форма. Основание выбирается
из проведенных продаж/поступлений с пагинацией. Показываются его аналитики,
оставшееся количество, исходные цена и НДС. Есть сохранение, проведение,
отмена, просмотр движений и документы возврата денег с отдельным проведением.
При отказе проведения ошибка сервера остается видна в редактируемой форме.

Схема дополняется идемпотентными `CREATE TABLE IF NOT EXISTS` при обычной
инициализации: `goods_returns`, `goods_return_lines`, `goods_return_refunds`.
Существующие документы и ресурсы не переписываются.

## Исполняемые проверки

RET-001–RET-005 переведены из бизнес-описаний в API-сценарии в
`runner/trade_harness/build_catalog.py`. Каталог и
`TRADE_ACCOUNTING_SCENARIOS.md` перегенерированы. Теперь исполняются 37 из 150
сценариев; 113 остаются заблокированными. Проверка незавершенного контракта
в `test_trade_catalog_guards.py` переведена на RET-006 и продолжает запрещать
ложный успешный результат. Сверка с выполнением в 1С не заявляется.

Команды из корня проекта (в этом окружении Python находится в
`F:\2026f\ctm3\.python\python.exe`):

```powershell
python runner/trade_harness/suite.py run --ids RET-001,RET-002,RET-003,RET-004,RET-005 --report data/trade-harness/stage2-report.json
```

проверки используют замоканный API; учетные цепочки исполняются реальным API
на изолированных SQLite-базах.

Итог: 131 backend-тест прошел (104 существующих + 5 новых сценариев каталога
+ 22 дополнительных проверки возвратов); 37 исполняемых торговых сценариев
прошли; 40 браузерных тестов прошли (37 существующих + 3 новых). TypeScript

## Границы

Возврат денег уменьшает аванс в разрезе первого этапа; распределения обычной
оплаты по конкретным накладным здесь нет. Возвраты работают с товарными
строками с материалом и единицей измерения. Корректировки цен RET-006/007 и
закрытые периоды RET-008 остаются следующими задачами.

Новые документы пока не включены в протокол межузлового обмена; их проведение
и проверка выполняются в одной базе CTM. PostgreSQL и внешние интеграции в
этом этапе не проверялись. Перед развертыванием в синхронизируемом контуре
нужен отдельный этап поддержки обмена возвратами.
