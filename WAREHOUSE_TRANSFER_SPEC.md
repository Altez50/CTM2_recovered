# Спецификация документа «Перемещение ТМЦ» между складами

Версия: 0.1  
Дата: 2026-09-19  
Статус: **в реализации (P0 частично)**  
Основание: отдельный документ перемещения и отдельное измерение «Склад» в
текущих исходниках не найдены.

Реализация от 2026-09-21: создан справочник `warehouses`, в поступлениях и
списаниях реквизит формы «Склад» стал ссылочным (`warehouse_id`), а старый
текст `warehouse` сохраняется в БД только как исторический снимок. При запуске
старые значения сопоставляются со справочником внутри организации, движения
регистра получают тот же `warehouse_id`. Добавлены документ перемещения,
парные движения, отбор остатков по складу, базовый web-интерфейс и синхронизация.
Оставшиеся пункты Definition of Done (в том числе обязательность ссылки в API
для новых поступлений/списаний, полный журнал `DocListConfig`, E2E и проверка
PostgreSQL) ещё не закрыты.

---

## 1. Результат обследования (AS-IS)

В системе есть документы:

- «Поступление ТМЦ» — `goods_receipts`, `/api/goods/receipts`;
- «Списание ТМЦ» — `goods_issues`, `/api/goods/issues`.

Они не являются перемещением между складами:

1. В `api/models/goods.py` тип документа ограничен значениями `receipt` и
   `issue`; модели с двумя складами нет.
2. В `api/database.py` есть таблицы `goods_receipts`, `goods_issues` и их
   строки, но нет `goods_transfers`.
3. Проведение поступления/списания в `api/goods_services.py` создаёт одно
   складское движение и движение во взаиморасчётах. Для внутреннего перемещения
   взаиморасчёты возникать не должны.
4. `inventory_register` хранит измерения `material_id`, `object_id`, `unit_id`,
   но не хранит `warehouse_id`. Поэтому даже пара «списание + поступление» не
   позволяет получить остатки по складам.
5. Поле `material_consumptions.warehouse` — свободный текст отдельного
   документа расхода материалов; оно не является ссылкой на склад и не решает
   задачу складского учёта.
6. В web-клиенте, маршрутах, боковом меню, конфигурации списков и механизме
   синхронизации поддержаны только поступления и списания.

Создавать перемещение двумя существующими документами нельзя: операция не будет
атомарной, породит ложные взаиморасчёты, допускает расхождение количества и
стоимости между расходом и приходом и не связывает обе стороны одной операцией.

## 2. Цель и границы

Добавить документ **«Перемещение ТМЦ»**, который одной транзакцией переносит
материалы со склада-отправителя на склад-получатель и создаёт равные по
количеству и стоимости расходное и приходное движения.

В объём P0 входят:

- справочник складов;
- склад как измерение регистра ТМЦ;
- CRUD, проведение, отмена проведения, копирование и пометка на удаление;
- журнал и форма документа в web-клиенте;
- просмотр движений документа;
- остатки и движения ТМЦ с отбором по складу;
- синхронизация справочника и документа;
- backend- и E2E-тесты.

Не входят в P0:

- ордерная схема и состояние «товар в пути»;
- адресное хранение, ячейки, партии, серии и сроки годности;
- резервирование;
- печатная форма и импорт из Excel (можно добавить в P1);
- межорганизационная передача. Она должна оформляться реализацией и
  поступлением, а не внутренним перемещением.

## 3. Принятые функциональные решения

### 3.1. Склад — самостоятельная аналитика

Склад нельзя подменять строительным объектом. В регистре одновременно
сохраняются:

- `warehouse_id` — физическое место хранения;
- `object_id` — строительный объект/аналитика затрат (может быть `NULL`).

Один склад принадлежит одной организации. Документ разрешает перемещение
только между складами одной организации.

### 3.2. Реквизиты документа

Шапка:

| Поле | Тип | Обязательность | Правило |
|---|---|---:|---|
| `number` | string(100) | да после записи | Автонумерация `ПМ-0001`, ручное значение допускается |
| `date` | date | да | Дата движений регистра |
| `organization_id` | FK organizations | да | Владелец обоих складов |
| `source_warehouse_id` | FK warehouses | да | Склад-отправитель |
| `destination_warehouse_id` | FK warehouses | да | Склад-получатель, отличается от отправителя |
| `source_object_id` | FK objects | нет | Аналитика расходного движения |
| `destination_object_id` | FK objects | нет | Аналитика приходного движения |
| `responsible_id` | FK persons | нет | Ответственный |
| `description` | string(2000) | нет | Комментарий |
| `is_posted`, `posted_at` | system | — | Состояние проведения |
| `marked_for_deletion` | system | — | Мягкое удаление |
| `uuid`, timestamps, `is_deleted` | system | — | Синхронизация |

Табличная часть:

| Поле | Тип | Обязательность | Правило |
|---|---|---:|---|
| `line_number` | integer | да | Уникален в документе, начиная с 1 |
| `material_id` | FK materials | да | Группа материалов недопустима |
| `name` | string(500) | да | Снимок наименования для устойчивого отображения |
| `unit_id` | FK units | да | Единица материала; конвертация единиц вне P0 |
| `quantity` | decimal/float | да | Строго больше 0 |
| `unit_cost` | decimal | системное | Средняя стоимость на складе-источнике на дату проведения |
| `sum` | decimal | системное | `quantity * unit_cost`, округление до 2 знаков |
| `note` | string(1000) | нет | Примечание |
| `uuid`, timestamps, `is_deleted` | system | — | Синхронизация |

`unit_cost` и `sum` в форме доступны только для чтения и окончательно
определяются при проведении. НДС в перемещении не рассчитывается.

### 3.3. Проверки

При сохранении:

1. Организация и оба склада существуют и не помечены на удаление.
2. Оба склада принадлежат выбранной организации.
3. Склад-отправитель не равен складу-получателю.
4. Есть хотя бы одна строка; материал, единица и положительное количество
   заполнены.
5. Одинаковые пары `(material_id, unit_id)` либо запрещаются с понятной ошибкой,
   либо предварительно сворачиваются. Для P0 принято **запрещать дубли**.

При проведении дополнительно:

1. Остаток проверяется по комбинации
   `(warehouse_id, source_object_id, material_id, unit_id)` на дату документа.
2. Требуемое количество агрегируется по материалу до проверки, чтобы несколько
   строк не могли отдельно пройти контроль одного остатка.
3. Отрицательный остаток запрещён. Ошибка содержит номер строки, материал,
   требуемое количество и доступный остаток.
4. Повторное проведение уже проведённого документа возвращает `400`.
5. Проведённый документ нельзя менять или помечать на удаление до отмены
   проведения.

### 3.4. Стоимостная оценка

Стоимость остатка определяется как:

```text
quantity_balance = SUM(quantity_income - quantity_expense)
sum_balance      = SUM(sum_income - sum_expense)
average_cost     = sum_balance / quantity_balance
```

Для каждой строки обе записи перемещения получают одинаковую сумму:

```text
transfer_sum = round(quantity * average_cost, 2)
```

Это сохраняет общую стоимость запасов при перемещении. Текущее вычисление
средней цены в `inventory_balances()` по формуле `sum_income / quantity_income`
должно быть исправлено на стоимость остатка; иначе после расходов и перемещений
отчёт будет показывать неверную цену.

Если количественный остаток положителен, но стоимость остатка равна нулю,
перемещение допускается с нулевой стоимостью. Если количество равно нулю или
меньше требуемого — проведение запрещается.

### 3.5. Движения при проведении

На одну строку документа создаются **две** записи `inventory_register` с
`recorder_type = 'goods_transfer'`:

| Сторона | `warehouse_id` | `object_id` | Приход | Расход | Сумма прихода | Сумма расхода |
|---|---|---|---:|---:|---:|---:|
| Отправитель | `source_warehouse_id` | `source_object_id` | 0 | quantity | 0 | transfer_sum |
| Получатель | `destination_warehouse_id` | `destination_object_id` | quantity | 0 | transfer_sum | 0 |

Для однозначности парных записей добавить в регистр `movement_side` со
значениями `source` / `destination` (для старых движений — `NULL`). Уникальность
логической записи перемещения:
`(recorder_type, recorder_id, line_number, movement_side)`.

Проведение выполняется одной транзакцией:

1. Повторно прочитать документ и проверить состояние.
2. Проверить реквизиты и остатки.
3. Удалить прежние движения этого регистратора (идемпотентная защита).
4. Записать расход и приход по каждой строке.
5. Зафиксировать рассчитанные `unit_cost`/`sum` в строках.
6. Установить `is_posted = 1`, `posted_at` и зарегистрировать sync-изменение.
7. Сделать один `commit`; при любой ошибке выполнить `rollback`.

Документ **не создаёт** записей в `mutual_settlements_register`, платёжном
календаре или регистрах затрат.

Отмена проведения одной транзакцией удаляет обе стороны движений и снимает
признак проведения. Повторная отмена непроведённого документа возвращает `400`.

## 4. Модель данных

### 4.1. Справочник `warehouses`

```sql
CREATE TABLE IF NOT EXISTS warehouses (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    code TEXT NOT NULL DEFAULT '',
    name TEXT NOT NULL,
    organization_id INTEGER NOT NULL,
    default_object_id INTEGER,
    responsible_id INTEGER,
    address TEXT,
    marked_for_deletion INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    modified_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    uuid TEXT NOT NULL UNIQUE,
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    is_deleted INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY (organization_id) REFERENCES organizations(id),
    FOREIGN KEY (default_object_id) REFERENCES objects(id),
    FOREIGN KEY (responsible_id) REFERENCES persons(id)
);
```

Обязательные индексы: `uuid`, `(organization_id, name)`,
`(organization_id, code)`. Код может быть пустым; если заполнен, его
уникальность контролируется внутри организации на сервисном уровне одинаково
для SQLite и PostgreSQL.

Добавить `warehouses` в модели и API справочников, список полей web-клиента,
`UUID_READY_TABLES`, `REFERENCE_TABLES` и sync-конфигурацию.

### 4.2. Документ

Создать таблицы:

- `goods_transfers` — реквизиты шапки из раздела 3.2;
- `goods_transfer_lines` — строки из раздела 3.2, FK
  `transfer_id REFERENCES goods_transfers(id) ON DELETE CASCADE`.

Индексы:

- `goods_transfers(date)`;
- `goods_transfers(source_warehouse_id, date)`;
- `goods_transfers(destination_warehouse_id, date)`;
- `goods_transfer_lines(transfer_id, line_number)`;
- уникальный `uuid` на обеих таблицах.

### 4.3. Расширение регистра и существующих документов

Добавить nullable-колонки:

```text
goods_receipts.warehouse_id
goods_issues.warehouse_id
inventory_register.warehouse_id
inventory_register.movement_side
```

После миграции `warehouse_id` обязателен для новых поступлений, списаний и
перемещений. Nullable в физической схеме сохраняется только для безопасного
обновления старых БД; обязательность контролируется API.

Остатки, движения, контроль доступности и отчёт `InventoryBalancesReport`
группируются и фильтруются по `warehouse_id` вместе с текущими измерениями.

### 4.4. Миграция существующих данных

Миграция должна быть идемпотентной и работать на SQLite и PostgreSQL:

1. Создать таблицы и nullable-колонки.
2. Для каждой организации, у которой есть старые складские документы, создать
   склад `Основной склад` с детерминированным кодом `MAIN` (если его ещё нет).
3. Заполнить `goods_receipts.warehouse_id` и `goods_issues.warehouse_id` этим
   складом организации.
4. Заполнить `inventory_register.warehouse_id` через документ-регистратор.
5. Строки регистра, для которых организацию определить нельзя, оставить без
   склада и вывести их количество в журнал запуска. Запуск приложения не
   должен молча приписывать их произвольной организации.
6. До включения обязательной серверной валидации проверить, что неразобранных
   активных движений не осталось, либо оформить для них явно выбранный склад.

Не использовать пересоздание или удаление пользовательской БД. Изменения
добавляются через `SCHEMA_TABLES_SQL`, `SCHEMA_INDEXES_SQL` и идемпотентные
функции `ensure_runtime_schema()` по принятому в проекте подходу.

## 5. API

### 5.1. Справочник складов

Расширить общий API справочников видом `warehouses`. Требуются список, чтение,
создание, изменение, пометка/снятие пометки удаления. В списке поддержать
`organization_id`, `search`, пагинацию, сортировку и быстрые отборы.

### 5.2. Документ перемещения

Базовый путь: `/api/goods/transfers`.

| Метод | URL | Назначение | Роли |
|---|---|---|---|
| GET | `/transfers` | Журнал с пагинацией/фильтрами | authenticated |
| POST | `/transfers` | Создание | manager, admin |
| GET | `/transfers/{id}` | Карточка со строками | authenticated |
| PUT | `/transfers/{id}` | Изменение черновика | manager, admin |
| DELETE | `/transfers/{id}` | Пометка черновика на удаление | manager, admin |
| POST | `/transfers/{id}/post` | Проведение | admin |
| POST | `/transfers/{id}/unpost` | Отмена проведения | admin |
| POST | `/transfers/{id}/copy` | Копия-черновик текущей датой | manager, admin |
| GET | `/transfers/{id}/movements` | Две стороны складских движений | authenticated |

Фильтры списка: `date_from`, `date_to`, `organization_id`,
`source_warehouse_id`, `destination_warehouse_id`, `material_id`, `is_posted`,
`search`, быстрые фильтры, `sort_by`, `sort_order`, `page`, `page_size`.

Поиск охватывает номер, описание и наименования обоих складов. В ответе списка
возвращать денормализованные `organization_name`, `source_warehouse_name`,
`destination_warehouse_name`, `responsible_name`, количество строк и общую
стоимость.

`InventoryRecorderType` расширить значением `goods_transfer`, а просмотрщик
движений — видом `transfer`. Для перемещения секция взаиморасчётов возвращает
пустой массив.

Ошибки бизнес-правил возвращаются как `400`, отсутствие сущности — `404`,
недостаток роли — `403`. Тексты пользовательских ошибок — на русском.

## 7. Синхронизация

Добавить типы сущностей и порядок зависимостей:

```text
warehouses             после organizations, objects, persons
goods_transfers        после warehouses, materials, units
goods_transfer_lines   перед восстановлением движений документа
```

В `sync_runtime.py` требуются сериализация, upsert, мягкое удаление и
восстановление движений проведённого документа. Ссылки передаются UUID-ами, а
не локальными числовыми id.

При получении проведённого перемещения принимающий узел пересоздаёт обе стороны
`inventory_register` детерминированно. Sync не должен создавать
`mutual_settlements_register` для перемещения.

Повысить `SYNC_SCHEMA_VERSION` только вместе с поддержкой новых сущностей на
обеих сторонах обмена. Несовместимая версия должна отклоняться явно.

## 8. Безопасность и целостность

- Сохранить текущую матрицу ролей ТМЦ: чтение — авторизованные, запись —
  `manager/admin`, проведение — `admin`.
- Все имена таблиц, сортируемых полей и быстрых фильтров задаются whitelist;
  пользовательские значения передаются параметрами SQL.
- Проверка остатка, создание двух движений и изменение статуса выполняются в
  одной транзакции БД.
- API не доверяет рассчитанным клиентом цене и сумме.
- Помеченный на удаление склад нельзя выбирать в новом документе. Удаление
  склада с активными документами/движениями остаётся только мягким.
- Проведение не должно менять общий количественный и стоимостный остаток по
  организации и материалу; меняется только разрез склада/объекта.

## 9. Тесты и критерии приёмки

### 9.1. Backend

Обязательные тесты:

1. CRUD черновика, автонумерация, копирование и мягкое удаление.
2. Валидация разных складов и их принадлежности одной организации.
3. Запрет пустых строк, нулевого количества и дублирующего материала/единицы.
4. Успешное проведение создаёт ровно две записи на строку.
5. Расход источника равен приходу получателя по количеству и сумме.
6. Движения во взаиморасчётах и платежах отсутствуют.
7. Недостаточный остаток полностью откатывает транзакцию.
8. Несколько строк не обходят агрегированный контроль остатка.
9. Отмена проведения удаляет движения; повторное проведение даёт тот же
   результат без дублей.
10. Запрет изменения/удаления проведённого документа.
11. Проверка RBAC для viewer/foreman/manager/admin.
12. Остатки и движения фильтруются и группируются по складу.
13. Общий остаток организации до и после перемещения совпадает.
14. Стоимость остатка и средняя цена корректны после цепочки
    `поступление → частичное списание → перемещение`.
15. Sync round-trip сохраняет документ, строки, ссылки на склады и движения без
    дублей.
16. Миграция старой БД идемпотентна и не теряет существующие движения.
17. Контракты выполняются на SQLite; PostgreSQL-путь покрыт доступным
    интеграционным прогоном или отдельной CI-задачей.

### 9.2. E2E

Сценарий Playwright:

1. Администратор создаёт два склада одной организации.
2. Проводит поступление материала на первый склад.
3. Создаёт перемещение части количества на второй склад и проводит его.
4. Открывает движения и видит расход первого и приход второго склада.
5. Отчёт остатков показывает уменьшение первого, увеличение второго и
   неизменный общий итог.
6. Отмена проведения возвращает исходные остатки.
7. Менеджер может записать черновик, но получает `403` при проведении.

### 9.3. Definition of Done

Функция принята, когда:

- документ доступен из меню, полный CRUD/lifecycle работает;
- склад обязателен в новых поступлениях, списаниях и перемещениях;
- остатки ведутся и отображаются по складам;
- парные движения атомарны и равны по количеству и стоимости;
- взаиморасчёты от перемещения не возникают;
- старые данные мигрированы без потерь;
- sync поддерживает новые сущности;
- `python verify.py` проходит полностью, включая новые backend- и E2E-тесты;
- документация API и пользовательская документация обновлены.
