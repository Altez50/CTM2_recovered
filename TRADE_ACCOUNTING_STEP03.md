# STEP-03 — надежность проведения и доступ

Реализован ровно пакет LIFE-005, LIFE-006, LIFE-008, LIFE-009, LIFE-010.
Изменения подготовлены в рабочем дереве для ревью. Развертывание, коммиты,
изменение production/рабочих баз/UTrecover и запуск следующего пакета не
выполнялись. Исполнитель не редактировал `implementation_queue.json`.

## Исполняемые контракты

| ID | Проверяемое поведение и исходные ожидания |
|---|---|
| LIFE-005 | Поступление 10 × 100 без НДС проведено; попытка сменить цену на 200 отклоняется. Стоимость 1000 и долг 1000 сохраняются. |
| LIFE-006 | После поступления 10 и продажи 8 отмена поступления отклоняется; остаток 2 сохраняется. |
| LIFE-008 | Пользователь с ролью «Только чтение» и доступом к A не проводит документ A и не читает документ B; изменение регистров 0. |
| LIFE-009 | Запас 1, два отдельных HTTP-клиента продают по 1: одно проведение, один отказ HTTP 400, итоговый запас 0. |
| LIFE-010 | Запас 10, продажа 3, ошибка после вставки складского движения: документ не проведен, запас 10, новый долг 0, частичных записей 0. |

Авторские действия и ожидания в каталоге сохранены. Изменены только признаки
исполняемости этих пяти сценариев. Сборщик доказательств восстанавливает
предыдущие признаки в копии JSON в памяти и сверяет SHA-256 с каталогом до
STEP-03: это подтверждает неизменность всех 150 бизнес-контрактов. Сам каталог
при такой проверке не переписывается. LIFE-007 и LIFE-011 остались заблокированы.

## Проведение и отмена

Проверка запрета редактирования проведенного документа уже существовала;
новая приемка подтверждает ее фактические ресурсы склада и расчетов.
Отмена поступления теперь отклоняется при зависимом расходе в том же разрезе
с даты поступления. Это консервативное правило COST-005: дополнительные
поступления, позволяющие избежать отрицательного остатка, не разрешают
незаметно изменить себестоимость уже проведенного расхода. Сначала отменяются
зависимые документы, затем основание. Автоматической перепроводки нет.

Существующая блокировка склада сериализует продажи последнего остатка.
Проверка LIFE-009 использует два TestClient, разные сессии авторизации и
отдельные соединения. Общая строка сессии не сериализует запросы вместо склада. Первый
запрос приостанавливается после чтения остатка внутри удерживаемой транзакции,
второй запускается до ее освобождения; затем оба завершаются. Это проверка
реального HTTP/сервисного пути, а не последовательная имитация конкуренции.

Сохранение/удаление/проведение/отмена поступлений и продаж, а также затронутые
операции платежей получают явный rollback при исключении. Перед чтением
изменяемого состояния блокируется заголовок; существующие блокировки склада
и общие блокировки договора сохраняются. Добавлены блокировки заголовка в
удаление перемещения и жизненный цикл платежных календарей/транзакций.

LIFE-010 вставляет реальное складское движение, затем тестовая обертка
соединения выбрасывает исключение. Проверяется откат на том же соединении,
флаг документа, оба регистра, остаток и задолженность. Повторный обычный
запуск проводится успешно. Обертка и управление паузами находятся только
в `current/api/tests/trade_lifecycle_support.py`; параметра fault injection
в производственном API нет.

## Организации и роли

Права хранятся отдельно от пользовательских настроек форм:
`users.organizations_restricted` и `user_organizations`.

- `organization_ids: null` — явный доступ ко всем организациям. Это совместимое
  значение для прежних пользователей после миграции.
- `organization_ids: [A, ...]` — доступ только к перечисленным организациям.
- `organization_ids: []` — нет доступа к торговым документам организаций.
- Роль `viewer` («Только чтение») читает разрешенные данные и не записывает
  торговые документы. `manager` готовит черновики; проведение/отмена требуют
  `admin`. Ограничение организаций действует и для администратора.

`get_current_user` читает роль и организации из БД на каждом запросе.
Изменение прав действует для уже выданного токена со следующего запроса;
значения из JWT или пользовательского JSON настроек не расширяют доступ.

Торговые маршруты получают соединение с аутентифицированным контекстом.
SQL не переписывается автоматически: сервисы явно добавляют ограничение
организаций перед группировкой, итогами, подсчетом страниц и выборкой строк.
Чтение по ID и операции изменения проверяют организацию документа отдельно.
Проверки распространяются на поступления, продажи, перемещения, возвраты,
возвраты денег, корректировки, начальные остатки, платежи и календари в
затронутом торговом контуре; также на движения, отчеты, Excel, копирование,
документы-основания и подбор платежей. Ограничение не зависит от фильтра UI.

Складские отчеты определяют организацию по регистратору, поэтому смена
нынешнего владельца склада не раскрывает исторические движения другой
организации. Для неизвестных/осиротевших регистраторов ограниченный доступ
закрыт; прежнее отображение таких строк для неограниченных пользователей
сохраняется. Платежи дополнительно проверяются по сохраненной организации
движений взаиморасчетов: смена владельца договора не раскрывает чужие факты.

Для платежных документов без собственной организации используется договор.
Ограниченным пользователям недоступны документы без определимой организации
и общие календари с чужими/неопределимыми строками. Старые общие календари и
платежи без договора сохраняют поведение для неограниченных пользователей.
Подбор зарплаты без организации требует неограниченного доступа. Общие
справочники товаров, единиц, характеристик/серий и контрагентов остаются
общими; организации, склады и договоры фильтруются по доступу.

Глобальная инженерная консоль таблиц требует администратора без ограничения
организаций. Общий обмен использует настроенный токен узла, а при отсутствии
такого токена — сессию неограниченного администратора; прежний анонимный
доступ при пустом SYNC_TOKEN закрыт, чтобы обмен не обходил торговые права.
Протокол межузлового переноса новых аналитик не расширялся.

Это ограничение торгового контура. Модель организаций строительных смет,
полевых документов и их отдельных регистров не перерабатывалась.

## API и формы

- `GET /api/users`: список пользователей, ролей и доступных организаций.
- `POST /api/users`: создание пользователя с ролью и явным доступом.
- `PUT /api/users/{id}/access`: изменение роли и списка организаций атомарно.
  Неизвестная организация отклоняется; собственный доступ текущего
  администратора через этот метод менять нельзя.
- Все три метода доступны неограниченному администратору. Пароль/хеш не
  возвращается в списке и результатах изменения доступа.
- `/administration/users`: форма «Пользователи и доступ», доступная через
  ссылку в шапке. Поддержаны создание, роль, отдельные организации, пустой
  список и «Все организации». Это обычная вкладка рабочего пространства.
- Формы поступления, продажи, перемещения и календаря показывают команды
  записи/проведения по роли; список платежей и общая панель списков учитывают
  чтение. Проведенное поступление нельзя сохранить и через команду шапки.
- Связь `based_on_*` продажи явно принимается API и проверяется по доступу
  к основанию, используя уже существующие поля БД.
