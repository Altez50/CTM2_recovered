## Учет и API

В проведении поступлений и реализаций проверяются организация и контрагент
договора. В платежах контрагент проверяется при сохранении и повторно при
проведении. Удаленные договоры использовать нельзя. Организация платежа
определяется договором; аванс требует договора с указанной организацией.

`POST/PUT /api/payments/transactions` принимает `allow_advance: boolean`.
По умолчанию `false`: оплата сверх открытого долга на дату платежа отклоняется,
включая превышение на одну копейку. `true` разрешает платеж до поставки и
переплату. Признак сохраняется в документе и передается при обмене.
Добавлена идемпотентная миграция `payment_transactions.allow_advance` с
нулевым значением для существующих записей.

Полная сумма платежа записывается единственным движением взаиморасчетов.
В разрезе организации, контрагента, договора, объекта и направления:

- долг = max(начисления − оплаты, 0);
- аванс = max(оплаты − начисления, 0).

Следующая поставка в том же разрезе автоматически уменьшает аванс. Договоры,
объекты и встречные направления друг друга не погашают. Отдельного документа
зачета нет; отмена и повторное проведение пересчитывают состояние по движениям.
Отмена поставки допускается при платежах с разрешенным авансом. Для обычных
оплат сохранена блокировка отмены поставки до отмены платежей того же разреза.

`GET /api/settlements/balance` возвращает неотрицательные `receivable_balance`,
`payable_balance` и новые `customer_advance`, `supplier_advance`.
`GET /api/settlements/turnover` добавляет `customer_advance_opening/closing`,
`supplier_advance_opening/closing`, `object_id`, `object_name`; строки разделены
также по объекту, чтобы аванс одного объекта не скрывал долг другого.
Для сверки оборотов применяется формула:
`долг_кон − аванс_кон = долг_нач − аванс_нач + начисления − оплаты`.

`GET /api/settlements/ledger` добавляет `customer_advance_running` и
`supplier_advance_running`; учитывает входящие остатки при фильтре `date_from`.
Отчет просроченных остатков учитывает оплаты и авансы с других дат в том же
разрезе. Его прежняя база определения просрочки по периоду регистра сохранена.
`GET /api/references/contracts` поддерживает совместные фильтры
`organization_id` и `counterparty_id`, до применения пагинации.

## Интерфейс

Форма платежа содержит организацию, договор и явное разрешение аванса.
Выбор договора ограничен владельцами; при смене организации или контрагента
договор сбрасывается. Для поступления и реализации также фильтруются договоры
и сбрасывается договор при смене владельцев. ОСВ показывает объект и авансы
на начало и конец периода, отдельные итоговые суммы; CSV содержит эти поля.

## Повторение проверок

В этом окружении используется Python `F:\2026f\ctm3\.python\python.exe`.

```powershell
python runner/trade_harness/suite.py run --ids DIM-004,DIM-005,PAY-007,PAY-008,PAY-009 --report data/trade-harness/stage1-report.json
python runner/trade_harness/suite.py run --implemented-only --report data/trade-harness/stage1-implemented.json
Set-Location current
python -m pytest -q --junitxml=../data/trade-harness/stage1-backend.xml
Set-Location web-client
npm run build
npm run test:e2e -- --workers=2
```

Дополнительные API-тесты `current/api/tests/test_trade_stage1.py` проверяют
запрет неразрешенных авансов, повторное проведение, смену владельца договора,
изоляцию объектов/договоров/направлений, копейки, исторические остатки,
просрочку, фильтры справочника, миграцию и сохранение признака в обмене.
Браузерные тесты используют замоканный API; учетные цепочки проверяются
отдельно реальным API с временной SQLite-базой.
