# CTM — ревью спецификаций и трассировка реализации

Дата ревью: 2026-09-02
Область: корневые `*_SPEC.md`, связанные task/plan-документы, `current/api`,
`current/web-client`, тесты и контур поставки.
Источник истины для статуса реализации: текущие исходники, включая существующие
незакоммиченные изменения. Историческая отметка «готово» без автоматической
проверки считается только заявлением, а не доказательством.

**Обновление реализации:** репозиторные gaps P0, найденные этим ревью, закрыты
2026-09-02. Добавлены 32 backend-контракта, 31 Playwright-проверка, CI и единая
команда проверки; import получил RBAC/lifecycle/limits/atomic preview-apply;
регистр — SQL pagination/grouping и полный CSV/XLSX export; production config —
fail-closed validation без встроенных паролей. Единственное внешнее действие P0 —
ротация ранее использовавшихся SSH credentials администратором инфраструктуры.

## 1. Итог

Спецификации хорошо описывают отдельные интерфейсы, но набор пока не образует
полный контракт продукта. P0 теперь создаёт воспроизводимый фундамент доверия к
данным и поставке; главные оставшиеся gaps относятся к учётной семантике P1,
незавершённым интерфейсам P2 и двум новым функциям P3.

Frontend собирается; 22 layout-теста дополнены девятью smoke-проверками основных
потоков. Backend имеет 32 изолированных контракта, включая CRUD/lifecycle,
детерминированные суммы, rollback импорта и полную выгрузку регистра. Это ещё не
заменяет широкую real-backend E2E матрицу всех форм.

## 3. Подтверждённые gaps

### P0 — статус после исправлений

1. **Backend/CI — закрыто.** `pytest` работает на временной SQLite БД; GitHub
   Actions и `verify.py` запускают syntax, tests, build и Playwright.
2. **Импорт — закрыто в объёме P0.** Проверяются роль, существование и lifecycle;
   запрос ограничен до и во время streaming; preview/apply использует savepoint,
   а строки, ссылки и родительский документ регистрируются для sync.
3. **Регистр — закрыто в объёме P0.** Count/totals/group/page исполняются в SQL,
   export обходит pagination и формирует настоящий XLSX. Наборы >50 строк
   проверяются контрактами.
4. **Конфигурация — репозиторная часть закрыта.** Fallback-пароли удалены;
   production требует сильные JWT/sync secrets, отключённый seed и явный CORS.
   **Остаток:** инфраструктурный администратор должен выполнить внешнюю ротацию.
5. **Acceptance-команда — закрыто.** `python verify.py --install` не использует
   production/shared database.

### P1 — учёт, права и целостность

1. Карточка себестоимости не включает `overhead_distribution`, поэтому не
   сходится с калькуляцией и рентабельностью (`R-REP1`).
2. Drilldown ячейки фактической себестоимости работы/объекта открывает только
   `actual_costs`, хотя значение включает также распределённые накладные.
3. `contract_value` вычисляется из `planned_cost`; прибыль фактически равна
   отрицательному отклонению. Источник договорной стоимости не определён.
4. Проведение табеля создаёт труд без надёжной атрибуции к работе (`work_id=0`).
5. Create/update/delete/restore cost-сущностей доступны любому
   аутентифицированному пользователю, тогда как calculate/post ограничены ролями.
   Единой RBAC-матрицы нет.
6. `_audit_log` не получает автора и подавляет ошибки; аудит не доказывает, кто
   изменил данные.
7. `unpost_cost_calculation` переводит расчёт в `draft` и удаляет результат,
   тогда как тестовый план/исторические заметки ожидают возврат в `calculated`.
   Требуется одно явное состояние автомата и контракт на сохранность результата.
8. В отчёте отклонений выбор `cost_element_name` недетерминирован (`LIMIT 1`
   без `ORDER BY`), а обработка помеченных элементов неодинакова между отчётами.

### P2 — незакрытые существующие спецификации

1. Restore endpoints реализованы не для всех списков, хотя общий UI-контракт
   применён ко всем 11 конфигурациям.
2. «Ввод на основании» переносит шапку, но не табличную часть; разрешённые пары и
   правила преобразования строк не утверждены.
3. Смета уже подключена к общему обмену, но иерархическая round-trip семантика
   (`parent_group_id`) не зафиксирована и не тестируется.
4. Табель и ТМЦ используют отдельные import/export пути. Флаги профиля
   `create_missing_*` не управляют фактическим применением; создание справочников
   не имеет единого preview/apply/audit контракта.
5. Инженерная консоль видит пользовательский `LIMIT` как наличие лимита, но не
   зажимает его до `MAX_ROWS`; запрос с большим LIMIT может вернуть больше
   специфицированного максимума.
6. Drilldown, списки, регистр и инженерная консоль не имеют автоматических
   security/performance/contract тестов.
7. Backend bootstrap выдаёт FastAPI deprecation warnings для `Query(regex=...)`;
   заменить на `pattern=` до обновления FastAPI, чтобы предупреждения не скрывали
   реальные проблемы и будущий upgrade не стал блокером.

### P3 — запланировано, реализации нет

- Обновление цены материала при импорте накладной.
- Импорт нормативных баз ФЕР/ГЭСН Минстроя.

Обе функции массово изменяют НСИ и должны начинаться после P0/P1, с preview,
идемпотентностью, аудитом и тестируемым rollback/backup путём.

## 4. Недостающие продуктовые спецификации

Кроме нового `SECURITY_BASELINE_SPEC.md`, до масштабирования продукта нужны:

1. **Системная модель ролей и состояний документов** — единая таблица прав и
   state machine для каждого вида документа, включая import/copy/restore.
2. **Синхронизация и конфликты** — гарантии доставки, порядок зависимых сущностей,
   LWW/merge правила, повторы, tombstones, пакетные операции и наблюдаемость.
3. **Миграции и совместимость SQLite/PostgreSQL** — версия схемы, forward/rollback,
   контракт обновления узлов разных версий и обязательный dialect suite.
4. **Нефункциональные требования** — целевые объёмы, latency, пределы экспортов,
   timeouts, память и конкурентные изменения.
5. **Поставка и восстановление** — backup, проверка восстановления, RPO/RTO,
   ротация секретов, health/readiness и rollback релиза.

## 5. Правила статуса требований

- `Готово` — код найден, положительный/негативный/граничный автоматические тесты
  проходят, документация совпадает с контрактом.
- `Частично` — основной путь есть, но хотя бы один критерий или тест отсутствует.
- `Gap` — обязательное поведение отсутствует либо найден дефект контракта.
- `Решение` — реализация заблокирована продуктовым/учётным выбором.

Карта приоритетов и порядок поставки находятся в `DEVELOPMENT_PLAN.md`.
