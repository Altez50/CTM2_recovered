## 1. Цель и область применения

Инженерный раздел «Таблицы» — инструмент администратора/инженера для прямого
контроля данных базы без написания кода и без обращения к физической схеме.
Состоит из двух взаимосвязанных режимов:

1. **Просмотрщик таблиц** — навигация по таблицам справочников, документов и
   регистров с отображением **синонимов** (бизнес-наименований) вместо
   физических имён таблиц и полей. Только чтение.
2. **Консоль запросов** — редактор текста запроса на подмножестве SQL с
   использованием синонимов таблиц и полей (аналог «Консоли запросов 1С»):
   пользователь пишет запрос, видит списки доступных таблиц и их полей,
   выполняет запрос и получает таблицу результата с возможностью печати и
   сохранения.

### 1.1. Назначение

- Быстрая выверка данных «на месте» (движения по регистрам, состояние справочников,
  остатки, «куда делись деньги/объёмы»).
- Аналитические произвольные выборки, не покрытые штатными отчётами.
- Подготовка и отладка запросов до их внедрения в отчёты/сервисы.
- Снижение зависимости от физических имён: пользователь оперирует бизнес-терминами
  («Контрагенты», «Объекты», «Наименование», «Сумма»), как в 1С.

### 1.2. Контекст и аналогия с 1С

В 1С «Консоль запросов» работает на встроенном языке запросов 1С, где
физический слой скрыт, а имена объектов и реквизитов совпадают с
пользовательскими. В CTM физический слой — это SQLite (локальная разработка) и
PostgreSQL (продуктив, см. `db/dialect.py`, `db/postgres_backend.py`),
физические имена латинские (`counterparties`, `work_execution_register`).
Поэтому «синонимичный» слой в CTM — это **словарь отображения** бизнес-имён в
физические и **транслятор запроса**, подставляющий физические имена перед
выполнением (см. раздел 3.2.4, 4.4).

> **Важно о «T-SQL»:** под «подмножеством T-SQL» в данной спецификации понимается
> **ANSI-SQL-подмножество**, исполняемое движком БД (SQLite/Postgres).
> Собственно диалект T-SQL (Microsoft SQL Server: `TOP N`, `ISNULL`,
> `[квадратные идент.]]`, `GETDATE()`) движком **не поддерживается** и без
> адаптеров выполняться не будет (см. раздел 8, О7).

### 1.3. Место в интерфейсе

В боковое меню (`AppSidebarNew.vue`) добавляется новая секция **«Инженерия»**
(идентификатор `engineering`), видимая только роли `admin`. Секция содержит пункт
«Таблицы», раскрывающийся на два режима через переключатель вкладок внутри view:

```
/engineering/tables           — просмотрщик (по умолчанию)
/engineering/tables/console   — консоль запросов
```

Существующие секции меню: `documents` | `reports` | `references`.
Добавляется: `engineering` (в конец, после `references`). Для не-admin роль
секция и роуты скрыты (`meta.requiresAdmin` + guard в роутере, раздел 4.1).

## 3. Целевое поведение (TO-BE)

### 3.1. Режим «Просмотрщик таблиц»

#### 3.1.1. Дерево/список таблиц слева

1. Слева — древовидный список таблиц, сгруппированный по категориям:

   | Категория | Состав (синоним → физ. таблица) |
   |---|---|
   | Справочники | Контрагенты→`counterparties`, Объекты→`objects`, Работы→`works`, Физлица→`persons`, Организации→`organizations`, Договоры→`contracts`, Материалы→`materials`, Единицы→`units`, Спецификации работ→`work_specifications` |
   | Документы (шапки) | Сметы→`estimates`, Дневные отчёты→`daily_reports`, Табели→`timesheets`, Расход материалов→`material_consumptions`, Рапорты машин→`machinery_usage_reports`, Акты субподряда→`subcontract_acceptances`, Накладные расходы→`overhead_expenses`, Расчёт себестоимости→`cost_calculations`, Поступления ТМЦ→`goods_receipts`, Расход ТМЦ→`goods_issues`, Графики платежей→`payment_schedules`, Платежи→`payment_transactions` |
   | Табличные части | Строки сметы→`estimate_lines`, Строки дневного отчёта→`daily_report_lines`, Исполнители→`daily_report_executors`, Строки табеля→`timesheet_lines`, Строки расхода→`material_consumption_lines`, Строки машин→`machinery_usage_lines`, Строки субподряда→`subcontract_acceptance_lines`, Строки накладных→`overhead_expense_lines`, Строки поступления→`goods_receipt_lines`, Строки расхода ТМЦ→`goods_issue_lines`, Строки графика→`payment_schedule_lines` |
   | Регистры | Регистр работ→`work_execution_register`, Регистр зарплаты→`payroll_register`, Регистр ТМЦ→`inventory_register`, Взаиморасчёты→`mutual_settlements_register`, Регистр графиков→`payment_schedule_register`, Фактические затраты→`actual_costs`, Плановые затраты→`planned_costs`, Распределение накладных→`overhead_distribution`, Себестоимость вып.работ→`completed_works_cost` |

2. Технические таблицы исключены из просмотра: `users`, `sessions`,
   `sync_nodes`, `sync_changes`, `audit_logs`, `user_settings`, `constants`,
   `object_version_history`. Полный список исключений — в коде (вайтлист
   разрешённых таблиц, раздел 4.3).
3. Поиск по дереву (текстовое поле сверху) фильтрует как по синониму, так и по
   физическому имени (для разработчиков).
4. Выбор таблицы загружает её данные справа.

#### 3.1.2. Таблица данных справа

1. Колонки — поля таблицы, **заголовки = синонимы** (из метаданных, раздел 4.3).
   Служебные поля (`uuid`, `updated_at`, `is_deleted`) скрыты по умолчанию,
   включаются через «Настройка списка».
2. Переиспользуется единый список: `DataTable` + `ListCommandBar` +
   `ListSettingsDialog` (см. DOCUMENT_LIST_SPEC.md). Доступны:
   - серверная сортировка кликом по заголовку (цикл ASC→DESC→null);
   - быстрый отбор по колонкам (строка фильтров);
   - настройка состава колонок с сохранением (ключ `columns` в `user_settings`,
     `form_name` = `tables:<physical_table>`);
   - пагинация (page/page_size, по умолчанию 50);
   - полем быстрого поиска — поиск по наименованию/номеру/коду.
3. **Только чтение**: команды «Создать/Изменить/Провести/Удалить» скрыты.
   Доступны: «Обновить», «Фильтр», «Настройка списка», «Экспорт», «Печать».
4. Значения ссылочных полей (`*_id`) отображаются как **представление ссылки**
   (наименование связанной записи), а не голый идентификатор — как в штатных
   списках документов. Состав разрешённых ссылочных разворотов — в метаданных
   (раздел 4.3); неразвернутые ссылки показываются числом.
5. Булевы поля (`is_posted`, `marked_for_deletion`) — галочкой/прочерком;
   даты — в едином формате проекта; суммы — с форматированием.

### 3.2. Режим «Консоль запросов» (аналог 1С)

#### 3.2.1. Структура экрана

```
┌─────────────┬───────────────────────────────────────┐
│  Список     │  Редактор запроса (текст)             │
│  таблиц и   │  ───────────────────────────────────  │
│  их полей   │  [Выполнить] [Очистить] [Сохранить▼]  │
│  (дерево +  │  ───────────────────────────────────  │
│  поиск)     │  Результат: таблица + итоги           │
│             │  [Печать] [Экспорт ▸ xlsx/csv]        │
└─────────────┴───────────────────────────────────────┘
```

1. **Слева** — то же дерево таблиц, но раскрываемое на **поля** каждой таблицы
   (синоним поля + физическое имя + тип). Двойной клик по таблице/полю вставляет
   его синоним в редактор в позиции курсора.
2. **Поиск** по дереву фильтрует таблицы и поля.
3. **Справа сверху** — редактор текста запроса (моноширинный, нумерация строк,
   Tab = 2 пробела, базовая подсветка ключевых слов SQL).
4. **Панель действий**: «Выполнить» (Ctrl+Enter), «Очистить», «Сохранить»
   (в сохранённые запросы, раздел 3.2.5), «Форматировать» (опц., раздел 8 О8).
5. **Справа снизу** — результат: таблица (переиспользуется `DataTable`) + строка
   итогов (SUM/AVG/MIN/MAX/COUNT по числовым колонкам, переключаемо) + панель
   «Печать»/«Экспорт».

#### 3.2.2. Язык запросов (исполняемое подмножество)

Поддерживаемые конструкции (ANSI-SQL, совместимо с SQLite и Postgres):

| Конструкция | Пример |
|---|---|
| `SELECT` со списком полей/`*` | `SELECT Контрагенты.Наименование, Объекты.Адрес FROM ...` |
| `FROM` одна/несколько таблиц | `FROM Контрагенты JOIN Объекты ON Объекты.Владелец = Контрагенты.Ссылка` |
| `INNER/LEFT JOIN ... ON` | соединения по синонимам ссылок |
| `WHERE` с `=,<>,>,>=,<,<=,LIKE,IN,AND,OR,IS NULL,IS NOT NULL` | фильтрация |
| `GROUP BY` + агрегаты `COUNT,SUM,AVG,MIN,MAX` | группировка |
| `HAVING` | отбор по агрегату |
| `ORDER BY` | сортировка |
| `LIMIT N` (и `LIMIT N OFFSET M`) | ограничение выборки |
| Псевдонимы колонок `AS` | `SUM(Сумма) AS СуммаИтого` |
| Параметры `&Имя` (опц., раздел 8 О6) | `WHERE Дата >= &ДатаНач` |

**Запрещено**: `INSERT/UPDATE/DELETE/MERGE`, `CREATE/ALTER/DROP`,
`PRAGMA`/`ATTACH`/`DETACH`, `VACUUM`/`REINDEX`, обращение к техническим
таблицам (`users`, `sessions`, ...), любые DDL и модификация данных. Только
однострочный `SELECT` (раздел 4.4 — безопасность).

#### 3.2.3. Синонимы в запросе

1. В качестве имён таблиц в `FROM`/`JOIN` пользователь пишет **синоним**
   таблицы: `FROM Контрагенты`. Допускается и физическое имя (`counterparties`)
   — для разработчиков.
2. Поля — **синонимы**: `Контрагенты.Наименование`. Допускаются физические имена.
3. Ссылочные поля (внешние ключи) имеют человекочитаемый синоним-ссылку:
   `Объекты.Владелец` (вместо `owner_id`), `Строки сметы.Смета` (вместо
   `estimate_id`). В условии `ON`/`WHERE` такая ссылка сравнивается с `Ссылка`
   (PK) целевой таблицы.
4. Регистронезависимость синонимов: `КОНТРАГЕНТЫ` = `контрагенты` = `Контрагенты`.
5. Результирующие заголовки колонок: если задан `AS <псевдоним>` — он; иначе —
   синоним поля (или физическое имя при `*`/выражении).

#### 3.2.4. Трансляция запроса (как это работает внутри)

```
Текст пользователя (синонимы)
   │
   ▼  [парсер/транслятор, бэкенд]
SQL с физическими именами (параметризованный)
   │
   ▼  [read-only выполнение, LIMIT, таймаут]
Набор строк + имена колонок результата
   │
   ▼  [обратная подстановка синонимов в заголовки]
Таблица результата (синонимы)
```

Подробности реализации и анализ вариантов — раздел 4.4 и раздел 9
(анализ выполнимости).

#### 3.2.5. Сохранённые запросы

1. Кнопка «Сохранить» сохраняет текущий текст с именем (и опционально описанием).
2. Хранилище — `user_settings`, `form_name = 'tables:console'`, ключ `saved_queries`
   (JSON-массив `[{id, name, description, text, created_at}]`).
3. Список сохранённых запросов — выпадающее меню «Сохранённые▼» рядом с
   «Сохранить»: выбор загружает текст в редактор; «✕» — удалить.
4. Сохранение персональное (по `user_id`), как пользовательские настройки в 1С.

#### 3.2.6. Результат: печать и сохранение

1. После «Выполнить» результат отображается в `DataTable` с заголовками-синонимами.
2. «Печать» — HTML-макет (шапка с текстом запроса + таблица + итоги), открытие
   `window.print()`. Переиспользуется клиентский механизм печати.
3. «Экспорт ▸»: Excel (.xlsx) и CSV (.csv) — переиспользуется
   `utils/reportExport.ts`. Экспортируются видимые колонки и итоги.
4. Большие выборки: экспорт ограничен тем же `MAX_ROWS`, что и выполнение
   (раздел 4.4), с предупреждением о truncation.

## 4. Требования к бэкенду

### 4.1. Роуты и доступ

- Новый роутер `engineering` (или расширение `system`), все эндпоинты под
  `Depends(require_roles('admin'))`.
- В web-клиенте: `meta.requiresAdmin = true`; guard в `router.beforeEach`
  (`auth.role === 'admin'`).
- Меню: секция `engineering` рендерится только для admin (`v-if` в
  `AppSidebarNew.vue` по `auth.isAdmin`).

### 4.2. Каталог метаданных (синонимы)

Централизованный словарь в коде (модуль `api/engineering_metadata.py` или
расширение `models/`), декларативно описывающий разрешённые таблицы и синонимы:

```python
TABLE_CATALOG = {
    "counterparties": {
        "synonym": "Контрагенты",
        "category": "reference",
        "fields": {
            "id":        {"synonym": "Ссылка",        "type": "ref",   "hidden_default": False},
            "name":      {"synonym": "Наименование",  "type": "text"},
            "inn":       {"synonym": "ИНН",           "type": "text"},
            "parent_id": {"synonym": "Родитель",      "type": "ref",
                          "ref_table": "counterparties"},
            ...
        },
        "hidden_fields": {"uuid", "updated_at", "is_deleted"},  # служебные
    },
    ...
}
```

- Синонимы ссылочных полей человекочитаемые: `object_id` → `Объект`,
  `estimate_id` → `Смета`, `customer_id` → `Заказчик`, `contract_id` → `Договор`,
  `owner_id` → `Владелец`, `responsible_id` → `Ответственный`,
  `material_id` → `Материал`, `work_id` → `Работа`, `unit_id` → `Единица`.
- Общие синонимы служебных полей: `id`→`Ссылка`, `number`→`Номер`, `date`→`Дата`,
  `is_posted`→`Проведён`, `marked_for_deletion`→`Пометка удаления`,
  `created_at`→`Создан`, `modified_at`→`Изменён`, `price`→`Цена`,
  `quantity`→`Количество`, `sum`→`Сумма`.
- Поле без явного синонима — выводится физическое имя (fallback).

### 4.3. Эндпоинт чтения каталога

```
GET /api/engineering/catalog
→ { "categories": [
     { "id": "reference", "label": "Справочники",
       "tables": [ { "name": "counterparties", "synonym": "Контрагенты",
                     "fields": [ {"name":"id","synonym":"Ссылка","type":"ref"}, ... ] } ] },
     { "id": "document", ... }, { "id": "register", ... } ] }
```

- Кэшируется на клиенте (один раз за сеанс).
- Используется и просмотрщиком, и консолью ( дерево таблиц/полей ).

### 4.4. Эндпоинт выполнения запроса (консоль)

```
POST /api/engineering/query
Body: { "text": "<запрос с синонимами>", "limit": 1000, "params": { "ДатаНач": "2026-01-01" } }
→ { "columns": [ {"name":"name","synonym":"Наименование","type":"text"}, ... ],
     "rows": [ {...}, ... ],
     "row_count": 123,
     "truncated": false,
     "elapsed_ms": 42 }
```

**Безопасность (обязательно):**

1. Роль `admin` только (раздел 4.1).
2. Парсинг: принять только **один SELECT**. Запретить `;` (несколько операторов),
   запретить ключевые слова модификации/DDL (см. 3.2.2). Незнакомая конструкция →
   400 с понятным сообщением.
3. Трансляция синонимов: подстановка физических имён по вайтлисту каталога
   (раздел 4.2). Незнакомый синоним → 400 «Таблица/поле не найдено: <имя>».
4. **Read-only выполнение**: открыть транзакцию явно (`BEGIN`), выполнить
   `SELECT`, затем `ROLLBACK` (никаких коммитов). Для SQLite — дополнительно
   использовать соединение в режиме `read_only`/`PRAGMA query_only = ON`, если
   доступно. Для Postgres — отдельное подключение к read-only роли либо
   `BEGIN READ ONLY`.
5. Защитный `LIMIT`: если в запросе нет `LIMIT`, добавить `LIMIT <limit>`
   (по умолчанию 1000, максимум `MAX_ROWS = 10000`). `limit` из запроса не может
   превышать `MAX_ROWS`.
6. Таймаут выполнения (по умолчанию 10 с): для SQLite — `conn.set_progress_handler`;
   для Postgres — `statement_timeout` в транзакции. Превышение → 408/400 с
   сообщением «Превышено время выполнения».
7. Параметры `&Имя`: именованные параметры приводятся к позиционным/`?` для
   SQLite и к `%(_name)s` для Postgres (через существующий слой диалектов).
   Значения валидируются по типу.
8. Технические таблицы (из чёрного списка раздела 3.1.1) запрещены даже в
   подзапросах (после трансляции проверка: все использованные физические имена
   входят в белый список каталога).
9. Заголовки колонок результата: обратная подстановка синонимов (физ.имя →
   синоним) по каталогу; для вычисляемых/`AS` — как задано.

### 4.5. Эндпоинт просмотра таблицы (просмотрщик)

```
GET /api/engineering/tables/{table_name}
    ?page=1&page_size=50&search=&sort_by=&sort_order=&f_<field>=...
→ { "columns": [...синонимы...], "rows": [...], "pagination": {...}, "total": N }
```

- `table_name` проверяется по белому списку каталога (раздел 4.2).
- Использует `resolve_sort`/`order_by_clause`/`apply_quick_filters` из
  `list_query.py` (вайтлист колонок строится из метаданных таблицы).
- Ссылочные поля разворачиваются `LEFT JOIN` до наименования (по описанию `ref`
  в каталоге) — аналогично штатным спискам.
- Только `SELECT`, без `is_posted`/`marked_for_deletion` модификаций.

### 4.6. Сохранённые запросы

Переиспользует существующие `GET/PUT/DELETE /api/system/user-settings/{form_name}`
с `form_name = 'tables:console'`, ключ `saved_queries`. Новых эндпоинтов не
требуется.

## 7. Критерии приёмки

1. Пользователь с ролью `admin` видит секцию «Инженерия» → «Таблицы»;
   не-admin не видит ни меню, ни роутов (403/редирект при прямом переходе).
2. Просмотрщик: выбор таблицы из дерева показывает данные с заголовками-синонимами,
   сортировкой, фильтрами, пагинацией и сохранением состава колонок.
3. Просмотрщик: ссылочные поля показывают представления ссылок; технические поля
   скрыты по умолчанию; команды редактирования скрыты (только чтение).
4. Консоль: запрос с синонимами (`FROM Контрагенты SELECT Наименование, ИНН`)
   выполняется и возвращает таблицу с заголовками-синонимами.
5. Консоль: `JOIN` по ссылочным синонимам (`ON Объекты.Владелец = Контрагенты.Ссылка`)
   работает; агрегаты `GROUP BY`/`SUM` и `ORDER BY`/`LIMIT` работают.
6. Консоль: попытка `INSERT/UPDATE/DELETE/DDL` или обращения к технической таблице
   отклоняется с понятным сообщением (400).
7. Консоль: превышение `MAX_ROWS` или таймаута возвращает truncated/ошибку без
   зависания сервера; read-only подтверждён (модификация невозможна).
8. Результат: печать (`window.print`) и экспорт в xlsx/csv формируют корректный
   документ с синонимами и итогами.
9. Сохранённые запросы сохраняются/восстанавливаются по пользователю.
10. Регресс: существующие списки/отчёты/печать не затронуты.

## 9. Анализ выполнимости аналога «Консоли запросов 1С»

### 9.1. Заключение: реализуемо, с оговорками по диалекту и безопасности

Полнофункциональный аналог достижим, т.к. все нижестоящие блоки уже есть в проекте:
слой БД с диалектами, интроспекция схемы, серверная сортировка/фильтр, настройки
пользователя, единый `DataTable` и печать/экспорт. Основная новая работа —
**словарь синонимов** и **транслятор запроса**.

### 9.2. Сопоставление 1С ↔ CTM

| Аспект | 1С | CTM (предлагаемо) |
|---|---|---|
| Язык запросов | встроенный язык 1С | ANSI-SQL (SQLite/Postgres) |
| Имена объектов | бизнес-имена = пользовательские | синонимы → физ.имена через каталог |
| Безопасность | платформа | read-only транзакция + вайтлист + таймаут + лимит строк |
| Результат | табличный документ | `DataTable` + экспорт/печать |
| Хранилище запросов | внешние обработки | `user_settings.saved_queries` |

### 9.3. Ключевой риск — корректность трансляции синонимов

Наивная замена подстрок/regexp **недопустима** (ломается на подстроках имён,
строках-литералах, псевдонимах). Варианты транслятора:

| Вариант | Достоинства | Недостатки | Рекомендация |
|---|---|---|---|
| **A. sqlglot** (Python) | полноценный AST, разбор SELECT, безопасный рерайт идентификаторов, транслирование диалектов | внешняя зависимость | **рекомендуется** — надёжнее всего |
| **B. sqlparse** | токенизация | рерайт идентификаторов ручной, меньше гарантий | приемлемо для MVP |
| **C. Регулярные выражения** | без зависимостей | хрупко, небезопасно | **не рекомендуется** |

Рекомендация: **вариант A (sqlglot)** на бэкенде. Парсер строит AST, транслятор
обходит узлы таблиц/колонок и заменяет синонимы по белому списку каталога, после
чего сериализует физический SQL. Это даёт корректную обработку алиасов, JOIN,
подзапросов и защищает от инъекций через идентификаторы.

### 9.4. Риск — диалект «T-SQL»

Пользователь ожидает «T-SQL», но движок — SQLite/Postgres. Чистый T-SQL
(`TOP`, `ISNULL`, `[...]`, `GETDATE`) **не выполнится**. Решения:

1. Документировать поддержку как **ANSI-SQL** и приводить примеры (рекомендация
   для MVP, раздел 3.2.2).
2. Опциональный слой адаптеров (О7): sqlglot умеет транслировать диалект
   `tsql` → `sqlite`/`postgres`, что снимает большую часть расхождений. Это
   позволяет реально принять «T-SQL-подобный» ввод.

Рекомендация: MVP — ANSI-SQL с понятными примерами; после MVP — включить
транслирование диалекта через sqlglot (О7), чтобы принять T-SQL-синтаксис.

### 9.5. Риск — безопасность и производительность

- Read-only гарантия: `BEGIN; ... ROLLBACK` обязательно + `query_only`/`READ ONLY`.
- Таймаут: SQLite `set_progress_handler`, Postgres `statement_timeout`.
- Лимит строк и размера ответа; запрет технических таблиц и модификации.
- Все эти меры стандартны и реализуемы поверх существующего слоя БД.

### 9.6. Трудоёмкость по блокам (относительная)

| Блок | Сложность | Переиспользование |
|---|---|---|
| Каталог метаданных (синонимы) | средняя (объём, но механика) | новое |
| Просмотрщик таблиц | низкая | `useDocumentList`, `DataTable`, `list_query` |
| Транслятор запроса (sqlglot) | средняя | новое |
| Выполнение + безопасность | средняя | слой БД, `dialect.py` |
| UI консоли (редактор + результат) | средняя | `DataTable`, печать, экспорт |
| Сохранённые запросы | низкая | `user_settings` |

### 9.7. Итог анализа

Реализация **целесообразна**: даёт администратору/инженеру самостоятельный
инструмент выверки и аналитики без вовлечения разработчиков, снижает
зависимость от физических имён (как в 1С), и не требует новых таблиц/инфраструктуры.
Главные условия успеха: (1) полноценный транслятор на sqlglot (не regexp),
(2) жёсткая read-only модель с вайтлистом/таймаутом/лимитом, (3) честная
документация диалекта (ANSI-SQL; T-SQL — через адаптер во 2-й итерации).
